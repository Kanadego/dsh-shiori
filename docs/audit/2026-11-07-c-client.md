## 二、逐条详述

### P1-1 重建轮询会话守卫失效（闭包 props 冻结）

- **现象**：`startRebuild` 的轮询循环用 `if (props.sessionId !== sid) return;` 判「会话已切换」。
- **位置**：`client/index.js:990-1023`（守卫在 `client/index.js:1002`；`client/index.js:997-999` 注释声称「会话切换即停轮询」）。
- **为什么是问题**：`startRebuild` 是某一次渲染里创建的闭包，`props` 是那次渲染的 props 对象，切换会话后组件虽以新 props 重渲，运行中的循环仍持有旧 props——`props.sessionId !== sid` 恒为 false，守卫永远不触发。轮询每 1500ms（`REBUILD_POLL_MS`，`client/index.js:919`）对旧会话发一次 getStatus，并在 `client/index.js:1014-1015` `setStatus(fresh)` / `setRebuildProgress(...)` 把旧会话的状态写进正在显示新会话的同一组件实例。切到别的 tab（组件卸载）也不会停：循环没有卸载 flag。
- **最小复现**：状态页选会话 A → 点「重建向量」→ 会话下拉切到 B → 观察 RPC 面板仍持续以 A 的 sessionId 发 getStatus；B 会话的状态页被 A 的 getStatus 结果覆盖（occupancy / 语义重建进度行显示 A 的数据）。
- **修复方向**：当前 sessionId 存 `useRef`（或复用 CandidatesTab 的 gen 守卫），循环每轮对比 ref；同时在组件卸载 cleanup 里置 stopped 标志终止循环。

### P1-2 六个 tab 的 load 无过期响应守卫

- **现象**：除 CandidatesTab 外，各数据 tab 的 `load` 直接 `setState(await dsh.call(..., props.sessionId, ...))`，没有 sessionId/gen 守卫。
- **位置**：`client/index.js:976-983`（StatusTab）、`client/index.js:1141-1146`（MemoryTab）、`client/index.js:1753-1758`（GraphTab）、`client/index.js:3494-3506`（TopicsTab）、`client/index.js:4221-4231`（FlashbacksTab）、`client/index.js:4357-4369`（TimelineTab）。
- **为什么是问题**：effect 依赖 `[props.sessionId]`，切换会话时旧 load 未返回、新 load 已发出，两个请求并发在飞；慢的旧响应后到会覆盖新会话的数据——页面显示 A 会话的记忆视图 / 图谱 / 专题列表 / 时间线 / 闪回统计，而选择器指向 B。FlashbacksTab 一次 load 串行发两个 await（getStatus + getGraph），竞态窗口最大。CandidatesTab 已有现成解法（`mark`/`isStale`，`client/index.js:2538-2542`，全部写动作与 load 都接了守卫），其余 tab 未跟进。
- **最小复现**：切到「专题」页选会话 A → 快速切会话 B，让 A 的 `memory_list_topics` 晚于 B 返回 → 列表显示 A 的专题。
- **修复方向**：把 CandidatesTab 的 mark/isStale 抽成共用 helper，六个 tab 的 load/各 catch 分支统一接入。

### P1-3 TopicsTab 详情串卡 + 保存写错目标

- **现象**：`readTopic(key)` resolve 时不校验 key 是否仍是当前打开的专题；`save()` 的写目标取 `detail.topic || opened`。
- **位置**：`client/index.js:3529-3537`（readTopic）、`client/index.js:3539-3556`（openTopic）、`client/index.js:3562-3580`（save，取 key 在 `client/index.js:3565`）。
- **为什么是问题**：点 A 再快速点 B，A 的 `memory_read` 响应后到 → `detail` 是 A 的正文而 `opened` 是 B，详情区标题与内容不符；此时点「编辑→保存」，`key = detail.topic || opened` 取到 A 的 topic（服务端 `memory_read` 结果带 `topic` 字段），draft 被写进 A——用户以为在改 B。若走 `opened` 分支则 expectedRevision 是 A 的 token，被服务端 revision 校验拦下报冲突。不会静默写坏 B（revision 校验兜底），但存在真实的「写错对象」路径。
- **最小复现**：专题页准备两个主题 A（正文大）、B → 点开 A 立刻点 B → 等 A 响应后到（详情显示 B 标题 + A 正文）→ 编辑 → 保存 → 成功提示为「主题 A 已保存」。
- **修复方向**：readTopic 发请求时记录 key（ref 或闭包计数），resolve 时与当前 opened 比对，不一致丢弃；save 前再校验一次 `detail.topic === opened`。

### P1-4 thin-core：服务端收、客户端拒、UI 无入口，渲染分支不可达

- **现象**：客户端本地校验器只放行 link / merge-topic，而服务端协议枚举含 thin-core；客户端预览卡却有完整的 thin-core 渲染支持。
- **位置**：拒绝点 `client/index.js:2397`（`proposal.kind 必须是 link / merge-topic`，该函数是 doPreviewOrganize（2666）与高级手写入口 doPreviewManual（2709-2717）的唯一校验口）；服务端 `src/plugin/protocol.mjs:182`（payload kind enum `["thin-core"]`）与 `src/organize/queue.mjs:1533`（`proposal.kind 必须是 link/merge-topic/thin-core`）；渲染分支 `client/index.js:2316`（PLAN_PREVIEW_TITLES）、`client/index.js:3110-3116`（正文）、`client/index.js:3199`（按钮「确认瘦身」）；测试 `test/plugin/client.test.mjs:4043`。
- **为什么是问题**：客户端所有 previewPlan 调用点（2661/2724/2742/2899）要么经 `validateOrganizeProposalLocal`（拒 thin-core），要么发 forgetting/archive-topic——UI 上不存在任何能产生 thin-core 预览卡的路径。0.2.3 为 thin-core 写的文案、正文、按钮样式及其测试覆盖的是一段从界面不可达的代码；同时服务端明确支持该 proposal 类型，属协议-客户端能力缺口。
- **最小复现**：在「整理与遗忘」高级调试区粘贴 `{"kind":"thin-core","before":"x","after":"y"}` → 本地即拒「proposal.kind 必须是 link / merge-topic」，请求根本不会发出；服务端直连 previewPlan 同形状 proposal 则可成功返回 planView（proposalKind:"thin-core"）。
- **修复方向**：要么在 UI 补 thin-core 发起入口（如记忆页 core 编辑区「瘦身预览」），要么在客户端明确裁掉该协议面并同步收紧 `planKindOf`/预览卡分支与测试——两边选一边，现状是三方各说各话。

### P2-1 GLOSSARY tab 对照表缺 2 个 tab

- **为什么是问题**：「最近变更」「闪回命中」两个 tab 在术语表无条目，后续文案改动没有对照基准，正是本席要求的「文案与一致性」类漂移。
- **最小复现**：对照 `docs/GLOSSARY.md:41` 表行数与 `client/index.js:4426` 数组长度（6 vs 8）。
- **修复方向**：GLOSSARY 第三章补两行（最近变更 / 闪回命中），或注明这两页不在 U0 定稿范围。

### P2-2 计划区同一规则两种说法

- **现象**：计划行提示写「organize 计划请从对应候选的『预览 / 合并进主题』流程执行」，区块头写「整理类计划请从对应候选的『预览整理计划 / 合并进主题』发起」；按钮实名是「预览整理计划」（`client/index.js:3263`）。
- **位置**：`client/index.js:3339` vs `client/index.js:3397`。
- **为什么是问题**：同一规则两个说法，且 3339 的「预览」不是任何按钮实名；对 thin-core 类 organize 计划这句还与 P1-4 叠加成误导（它并不能从候选流程发起）。
- **最小复现**：整理与遗忘页看任意 open organize 计划行的黄字与页头说明文字。
- **修复方向**：两处统一为按钮实名「预览整理计划 / 合并进主题」。

### P2-3 力导向布局无上限的主线程阻塞

- **现象**：`forceLayout` 每轮全点对斥力 O(n²)×120 轮，再加 ≤30 轮两两分离（`SEPARATION_ROUNDS`，同样是点对扫描）；`normalizeGraph` 对节点数无上限；服务端 getGraph 返回全部 active 卡（`src/plugin/management.mjs:299-309` 无 cap）。
- **位置**：`client/index.js:1471-1675`（布局主体；点对双循环在 `client/index.js:1499-1520` 一带）、调用点 `client/index.js:1762`（useMemo 化，仅图变化时重跑——这点是对的）。
- **为什么是问题**：数千卡 scope 下 120×n² ≈ 数亿次浮点运算全在主线程，切换到图谱页会长时间冻结面板；且 FlashbacksTab 也用同一份 getGraph 全量数据（4221）。
- **最小复现**：构造 2000+ active 卡的 scope（或临时把 ITERATIONS 提到 1200 观察量级）→ 打开「闪回图谱」→ UI 冻结秒级以上。
- **修复方向**：客户端设节点上限（超过阈值降级为圆形静布 + 提示），或网格化斥力 / 按 degree 稀疏化。

### P2-4 候选行每渲染全量 stableStringify

- **现象**：每行渲染都执行 `stableStringify(item)` 塞进折叠的「原始数据」details。
- **位置**：`client/index.js:3285`。
- **为什么是问题**：filter/search/collapsedKinds 任一 state 变化都触发整列表重渲；搜索框逐键输入即对全部候选做全量 JSON 稳定序列化（含嵌套 evidence），大队列下输入明显卡顿。details 折叠着也要先算出来。
- **最小复现**：候选队列塞几百条大 evidence 候选 → 在搜索框连续输入 → 逐键掉帧。
- **修复方向**：把「原始数据」拆成懒渲染子组件（details 首次展开才算），或 useMemo 按行缓存。

### P2-5 错误文案可能拼出字面量 undefined

- **现象**：`"proposal JSON 解析失败：" + e.message` 与 `"读取设置命名空间失败：" + (e && e.message)`。
- **位置**：`client/index.js:2709`、`client/index.js:3952`；对照防御写法 `client/index.js:998`、`client/index.js:4141`（`(e && e.message) || String(e)`）。
- **为什么是问题**：本仓 buildApi 会把 RPC 错误包成 Error（`client/index.js:677`），但这两处也接第三方 dsh 实现（仓库他处明确「防御第三方 dsh 实现抛错」，`client/index.js:4465` 一带注释）；rejection 是字符串/无 message 对象时，2709/3952 直接把 `undefined` 拼上屏。
- **最小复现**：`node -e "const e='timeout'; console.log('x：' + (e && e.message))"` → `x：undefined`；对应到 3952 的 BudgetsTab 读配置失败路径。
- **修复方向**：统一走 `sessionFailureOf` / `(e && e.message) || String(e)` 的既有防御写法。

### P2-6 TopicsTab 会话不可用口径与其他 tab 不一致

- **现象**：TopicsTab 的 load/readTopic/save catch 直接 `setError(e)` / `setSaveError(e)`，不经 `reportSessionUnavailable`。
- **位置**：`client/index.js:3501-3505`、`client/index.js:3531-3534`、`client/index.js:3578`。
- **为什么是问题**：其他 tab 会话级失败会上报面板层缓存（不再重复发同一 RPC，见 `client/index.js:4708-4721` 的 noteSessionUnavailable 契约）；TopicsTab 每次操作都重复吃同一条不可用错误，且 ErrorBox 显示原始 error 而非人话。
- **最小复现**：让会话不可用（另一实例持写锁）→ 专题页点「刷新」→ 原始错误直接挂在 ErrorBox，面板顶部黄条不出现。
- **修复方向**：三处 catch 接 `reportSessionUnavailable(e, props, setError)`。

### P2-7 useState 下标耦合与过期注释

- **现象**：测试按下标注入状态：CandidatesTab 的 `states[4]`=preview、`states[7]`=merge（`test/plugin/client.test.mjs:2364`、`test/plugin/client.test.mjs:2948`）；ShioriSection 的 `states[4]`=modeStatus（`test/plugin/ui-readonly.test.mjs:94`）。
- **位置**：声明序 `client/index.js:2468-2533`（CandidatesTab 17 个 useState，preview 在下标 4、merge 在下标 7）；`test/plugin/client.test.mjs:658` 注释写「states 承载其 7 个 useState」、`test/plugin/client.test.mjs:694-695` 写「data / error / busy / proposal / preview / previewError / guard」——实际早已是 17 个，7 个的说法只覆盖 states[0..6]。
- **为什么是问题**：任何人在这两个组件的下标 4 / 7 之前插入或删除一个 useState，测试会把状态注进错误的槽位——多数用例会挂，但个别宽松断言可能静默通过；「按 props 取值而不是按下标」的替代思路：给这两个 hook 槽位加具名 setter 注入口（如模块级导出 `__testHooks.previewState = [preview, setPreview]` 供测试显式引用），测试改按名字注入。
- **最小复现**：在 `client/index.js:2468` 与 2484 之间插入一个新 useState → 跑 `node --test test/plugin/client.test.mjs` → states[4] 相关系数全部错位报错。
- **修复方向**：短期先改过期注释（658/694 两处 + 2494 组件内「既有 7 个之后」注释）；长期按上述具名注入消掉下标依赖。

### P2-8 图谱节点键盘不可达

- **现象**：节点 `<g>` 只有 onPointerEnter/Leave/Up，无 tabIndex、无 onKeyDown、无 role。
- **位置**：`client/index.js:1879-1890`（渲染处；pointer 处理函数定义在 `client/index.js:1783-1794`）。
- **为什么是问题**：键盘 / 读屏用户无法选中节点、无法打开 NodeDetail（选中是查看卡详情的唯一入口）；同页搜索框有 Enter 处理（`client/index.js:1844`），说明键盘路径本有规划。
- **最小复现**：Tab 键遍历图谱页，焦点跳不过任何节点。
- **修复方向**：节点 g 加 `tabIndex=0` + Enter/Space 触发选中（与 pointer-up 共用同一 setSelected 路径）即可，不必做完整 roving tabindex。

## 三、已核查但不算问题的点（防下一轮重复劳动）

1. **内嵌 CSS 与 `client/shiori.css` 双份**：确为两份拷贝，但有专门一致性用例「bundle：内嵌 CSS 与 client/shiori.css 规则一致（去注释/压缩比较）」（`test/plugin/client.test.mjs:109`）逐条比对，本次全量通过——当前零漂移。行内 `style:{minWidth:0}`（`client/index.js:2916`、`client/index.js:3201`）与 `.dshi_root *{min-width:0}`（shiori.css 第 3 行）同值重复，无害。
2. **未引用函数/常量**：脚本扫描 `client/index.js` 全部 183 个函数声明与 26 个大写常量，引用数均 ≥2，无死声明。扫描脚本已用后即删（系统临时目录，未进仓库）。
