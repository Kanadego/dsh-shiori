# Shiori 记忆整理与温度冷却设计方案

> 日期：2026-11-21（晚修订：并入 §11.3 三条拍板、整理向导、存量种子 T；2026-11-22 追加 §9.2 施工进度与批次 4 拆线）
> 基线：`dsh-shiori@0.4.0`（`main`）
> 定位：Topic / Group 的二级索引折叠、间隔巩固温度调度、可逆冷却恢复与轻量演进路线
> 核心原则：**温度只负责可逆的曝光调度，不负责判断记忆的语义价值；AI 与用户负责语义判断。**

---

## 0. 结论摘要

本方案在**不推翻 Shiori 0.4.0 四层架构、双根隔离、CAS/Journal 事务与 Spark 双轨遗忘**的前提下，补齐 Topic 与 Group 的生命周期与曝光调度，同时修正初版讨论稿中温度模型过于简陋的问题：

1. **Spark（L2）**：继续沿用现有 `evergreen / ephemeral` 双轨与 `src/forgetting/decay.mjs`（`score ∈ (0, 1]`、`halfLifeDays = min(base * 2^useCount, max)`、60 天最小保护期），本方案不改其公式。
2. **Topic（L3）**：新增 `retention`（`standing / historical`）双轨生命周期（默认 `standing`），控制哪些长文档允许参与自动温度冷却。
3. **Group（二级索引）**：作为可选的二级目录与长文档拆分载体，不强制所有 Topic 归组；独立 Topic 与 `pinned` 组内 Topic 始终保留一轮直读通道。
4. **L1 顶层索引**：由 **独立活跃 Topic + 活跃 Group + 被 `pinned` 的组内活跃 Topic** 组成，并保留统一冷数据钩子行（`另有 N 篇冷专题，memory_search 可查`）。
5. **升级版温度模型（双派生值：稳定性 $S$ + 饱和热度 $T$）**：
   - 废除固定 45 天半衰期与线性截断 `+25`，改用**间隔巩固（$S$ 随冷态有效召回而增长并封顶）+ 渐近饱和加热（$T \leftarrow T + \alpha(100 - T)$）+ 全局时间冷却窗口去重**；
   - 精简无意义的分段，保留四档可操作区间（`active` / `cool` / `cold` / `frozen`），并让 `frozen` 与 `memory_search` 词法相关性排序正确协同（不再把所有归档 Topic 强行 `score: 0`）。
6. **消除 Group 温度耦合与唤醒死角**：Group 不独立维护“目录加热/衰减”的割裂状态，其有效温度直接由活跃成员与空组目录访问共同决定；子 Topic 自动恢复时同步处理父 Group 可见性，避免出现“已恢复活跃但在 L1 既无自身行也无父组入口”的悬空状态。
7. **严格边界与轻量原则**：不引入后台 LLM 改写正文、不每轮动态重构 L1（保 KV Cache）、不自动拆分/合并/删除文档；有损/结构性整理一律走 `queue → previewPlan → executePlan` 预览确认。
8. **未来可选轻扩展（预留接口、不抢跑）**：为 Topic 级轻量语义召回（仅作用于 `memory_search`，不动 L1）和基于冷读取后悔率的自适应参数学习保留事件与接口位。

一句话概括：

> **Spark 管原子事实，Topic 靠 `standing / historical` 分轨与（稳定性 $S$ + 热度 $T$）做可逆曝光调度，Group 承担二级折叠与长文拆解；系统保持轻巧、可审计、可回放，且绝不破坏 Prompt Cache 与 Markdown 人工可读性。**

## 1. 现状核对与真实痛点（0.4.0 基线）

基于 `D:/AIagent/shiori` 0.4.0 源码与主环境实测，落地本设计前必须正视以下事实：

### 1.1 已有基础设施（直接复用）

- **L1 渲染与硬预算**：`src/core/render.mjs` 的 `renderL1` 在读取时派生 `## 主题记忆索引`，`src/core/budget.mjs` 用 `hardCapChars`（默认 `10000`，主环境配 `14000`）派生 `softAt / hardAt`。
- **Group 与归档字段**：`src/storage/frontmatter.mjs` 与 `src/core/topics.mjs` 已支持 `archivedAt`、`group`（首个为主组，软上限 `3`）和 `pinned`；`src/core/groups.mjs` 与 `group_manage` 工具已就绪。
- **冷检索现行实现**：`src/service/index.mjs` 的 `search(query)` **默认已包含归档 Topic**（返回 `state: "archived"` 的摘要条目，`memory_read(key)` 可直接读全文）。
- **状态账本与水位采样**：`src/plugin/state.mjs` 已有 `projectionStore`、`waterlineStore`（节流防每轮写盘）、`queueStore`、`planStore`；`src/plugin/management.mjs` 已有 `archive-topic` 预览/执行计划通路。

### 1.2 尚缺的关键拼接点（施工前须补齐）

1. **L1 尚为全平铺渲染**：`renderL1` 目前 `requireExactKeys(input, ..., ["coreText", "topics"])`，尚不接收 `groups`，也不折叠非 `pinned` 的组内 Topic。
2. **元数据契约缺口**：`service/index.mjs` 的 `topic` metadata 白名单与 `tokenFor/checkSources`、`frontmatter.mjs`、`topics.mjs` 尚未接入 `retention` 与 `archiveOrigin`。
3. **归档排序硬伤**：`service/index.mjs` 当前把所有归档 Topic 一律记为 `score: 0` 并按 `key` 字母序排在末尾，既丢失关键词相关性排序，也无法体现冷/冻优先级差异。
4. **统计账本跨作用域问题**：`state.mjs` 当前按会话 `scopeId` 分文件存账；而 `global` Topic 可以在 `amber` 等任意人设下被读取，统计事件必须按 **Topic 真相所在的 `targetScopeId`** 归集。
5. **当前主要矛盾是文档过长而非索引条数**：主环境 `amber` 约 29 条 Topic，L1 派生索引仅约 1558 字符（远低于 9800 软水位），但 `heartbeat`（~2.0w 字）、`dsh-plugins`（~1.5w 字）、`model-channels`（~1.2w 字）单篇读取成本极高。**因此阶段 A（Group 二级折叠 + 长文档拆分导航）的优先级高于自动冷却。**

## 2. 核心数据契约（Truth vs Derived）

遵循 Shiori 双根隔离原则：**业务真相存 `dataRoot`（Markdown front-matter / `groups.json`），运行统计存 `stateRoot`（纯事件日志与派生缓存）**。

### 2.1 `dataRoot` 业务字段

| 字段            | 归属                                | 状态                        | 取值与语义                                                                                                                                                                 | 兼容默认值（缺省不写盘）                  |
| --------------- | ----------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `retention`     | Topic front-matter / Group 默认策略 | **拟新增**                  | `"standing"`（现行记忆：约定/守则/当前架构，**禁止自动冷却**）\| `"historical"`（历史记忆：旧方案/已完成阶段/事故归档，允许温度冷却）。Topic 可覆盖所属主 Group 的默认值。 | `"standing"`（保底护栏，存量永不误冷）    |
| `pinned`        | Topic front-matter                  | **已有**                    | `boolean`。`true` 表示：即使已入组也保留 L1 独立行，且**免于自动冷却**；不代表正文永久有效，不阻止用户手动归档。                                                           | `false`                                   |
| `group`         | Topic front-matter                  | **已有**                    | `string[]`，首个为主组。                                                                                                                                                   | `[]`（独立 Topic）                        |
| `archivedAt`    | Topic front-matter / Group 条目     | **Topic 已有 / Group 拟扩** | 规范 UTC ISO 时间串。有值即已冷却/归档（退出默认 L1 或组目录），缺省即活跃。                                                                                               | `undefined`（活跃）                       |
| `archiveOrigin` | Topic front-matter / Group 条目     | **拟新增**                  | `"manual"`（用户或受审确认归档，**绝不自动恢复**）\| `"auto-inactive"`（温度冷却，满足恢复条件可自动唤醒）。                                                               | 已有 `archivedAt` 但缺来源时按 `"manual"` |

> 注：`groups.json`（`GROUPS_VERSION` 升级为 `2` 或前向兼容扩展可选字段）中，每个组条目可带可选 `defaultRetention?: "standing" | "historical"`、`archivedAt?: string`、`archiveOrigin?: "manual" | "auto-inactive"`，读取缺省时分别为 `"standing"`、`undefined`、`undefined`。

### 2.2 温度与稳定性：纯派生调度值

- **不写入 `dataRoot` 的 Markdown front-matter**（否则每次读一次 Topic 就改写文件、触发 CAS revision 变更和不必要的 disk/journal 噪音）；
- **不写入 L1 系统提示词**（保证每轮 `shiori:core` 字节完全稳定，不破坏 KV Cache）；
- **全部由 `stateRoot` 的轻量事件流通过纯函数回放算出**，任何时候删掉派生缓存都能 100% 重算。

## 3. 目标 L1 索引模型与可见性规则

### 3.1 L1 顶层结构

L1 派生索引由三类活跃条目 + 一行冷数据钩子组成：

1. **未分组的活跃独立 Topic**（`group.length === 0 && !archivedAt`）：直接暴露一行，一轮 `memory_read` 直达。
2. **活跃 Group**（`!group.archivedAt`，且组内至少有一条非 `pinned` 活跃成员，或空组刚创建尚未冷却）：暴露一行组摘要（例如 `- [group:dev] 开发与配置 — DSH / 插件 / 发版（6 篇，含 2 篇置顶）`），先读组目录再按需读成员。
3. **被 `pinned` 的组内活跃 Topic**（`pinned === true && !archivedAt`）：即使已入组，仍保留独立 L1 行，保证高频核心记忆一轮直达。
4. **冷数据钩子**：沿用现有 `另有 N 篇冷专题，memory_search 可查`（仅当 `N > 0` 时出现）。

### 3.2 Group 二级目录读取入口

- 为 Agent 提供只读目录读取能力（扩展 `memory_read` 支持 `group: "<key>"`，或 `group_manage action="members"`——优先复用现有工具减少工具面增长，保持工具面简洁（当时 17 个；0.5 收口时 19 个，见 §12.4））：
  - 返回该 Group 内活跃成员列表：`key`、`title`、`summary`、`chars`、`updated`、`retention`、`pinned`；
  - 绝不注入正文；**读取目录本身不视为读取所有子 Topic**，不给子 Topic 加热。

### 3.3 冷却后的可见性与“父组冷却-子项唤醒”闭环

| 对象           | 冷却效果                                                         | 对 L1 的影响                             |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| 独立 Topic     | 退出 L1 默认索引，进入冷检索                                     | 移除对应 Topic 行，冷计数 `N + 1`        |
| 组内普通 Topic | 退出所属 Group 默认目录，进入冷检索                              | Group 行保留（只要组内还有其他活跃成员） |
| Group          | Group 整体退出 L1 默认导航（不级联修改子 Topic 的 `archivedAt`） | 移除 Group 行                            |

**恢复联动规则（2026-11-21 拍板）**：

- Group 不单独保存温度，有效温度 = 组内活跃成员 `T` 的最大值（§4.4）。组内任一普通成员经 `read` / `updated` 回到 `T >= 50`，Group 的有效温度随之 `>= 50`，下一轮评估就恢复 Group。
- **恢复的是导航，不是连坐成员**：Group 行与成员目录回到 L1，组内其余成员的 `archivedAt` 保持原样（该冷的继续冷，不跟着一起解冻）。
- 冷却不跨层级单轮级联，恢复同理：先恢复 Topic，Group 下一轮跟上；渲染期必须有兜底，不能出现「组已冷却、组内有活跃 Topic」的失明状态。
- 例外：Group 的 `archiveOrigin === "manual"`（用户手动封存整组）时永不自动恢复。被加热的成员在 L1 渲染期按独立条目降级露出，面板给出「所属组被手动封存，是否解除」的确认入口。

## 4. 升级版温度与冷却模型（轻量、可回放、无装饰分段）

相比初版讨论稿的“固定 45 天半衰期 + 线性 `+25` + 5 档空转等级”，本方案采用 **双派生变量（稳定性 $S$ + 饱和热度 $T$）**，依然保持 **纯函数、零黑盒、全事件可回放**，同时与 `src/forgetting/decay.mjs` 的遗忘哲学对齐。

### 4.1 核心公式（四则运算 + 指数衰减）

每条 Topic（按真相所在 `targetScopeId` + `key` 索引）维护两个派生状态：

- **稳定性（有效半衰期）$S$**：单位为天，范围 $[S_{\min}, S_{\max}]$（建议初始 $S_0 = 30$ 天，上限 $S_{\max} = 180$ 天）。代表“这条记忆多耐放”。
- **当前热度 $T$**：范围 $[0, 100]$。代表“这条记忆现在有多热乎”。

#### (1) 时间自然冷却

距上次有效加热事件经过 $\Delta t$ 天（$\Delta t = \max(0, (t_{\text{now}} - t_{\text{last}}) / 86400000)$）：

$$T(t_{\text{now}}) = T_{\text{last}} \cdot 2^{-\Delta t / S}$$

#### (2) 有效使用时的“渐近饱和加热”与“间隔巩固”

当一次事件在经过上述衰减得到当前热度 $T$ 后触发加热：

- **先巩固稳定性 $S$（越凉时被捞起来用，越证明长期价值；滚烫时连刷几乎不涨）**：

$$S_{\text{next}} = \min\Big(S_{\max},\; S \cdot \big(1 + g \cdot (1 - \frac{T}{100})\big)\Big)$$

  建议初始 $g = 0.5$（单次冷态召回最多延长 50% 半衰期；刚用完 $T=100$ 时延长度为 0）。

- **再饱和提升热度 $T$（替代硬加 25 再截断，保留高频区分度）**：

$$T_{\text{next}} = T + \alpha \cdot (100 - T)$$

### 4.2 分级事件规则（区分“强使用 / 普通读 / 纯搜索曝光”）

| 事件类型                                                          | 冷却窗口去重                                                                                                   | 对 $T$ 的效果                                          | 对 $S$ 的效果                    | 备注                                                                  |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------- | --------------------------------------------------------------------- |
| **`created`**（创建 Topic）                                       | —                                                                                                              | $T = 100$                                              | $S = S_0$（30 天）               | 进入最小年龄保护期                                                    |
| **`updated`**（`topic_append` / `memory_rewrite` 等实质内容修改） | 按时间窗口合并，但允许强刷新                                                                                   | $T = \max(T,\; 85)$                                    | 按上式巩固（并保底不低于 $S_0$） | 写入是最强的有效使用证据                                              |
| **`read`**（`memory_read(topic)` 完整读取正文）                   | **全局冷却窗口去重（如 `12h` 或 `24h`）**：同一 Topic 在窗口内无论同一会话还是多子会话多次读取，仅首次计入加热 | $\alpha = 0.35$（即 $T \leftarrow T + 0.35(100 - T)$） | 按间隔巩固公式更新 $S$           | 防止同日多会话连刷误唤醒                                              |
| **`search_hit`**（`memory_search` 命中但未点开）                  | 仅记录计数                                                                                                     | **不加热 $T$（0 增量）**                               | **不变**                         | 同 Spark `hitCount` 不续期原则；用于诊断“高频搜到却不点开 = 摘要写偏” |
| **`group_list`**（读取 Group 目录）                               | —                                                                                                              | **不给成员加热**                                       | **不变**                         | 仅记入空组防冷观测                                                    |
| **`manual_restored`**（人工恢复归档）                             | —                                                                                                              | 不强制重置 $T$                                         | 保持原 $S$                       | 遵守恢复后最小保护期，避免刚恢复次日又被自动冷回                      |

> **为什么改为全局时间窗口去重（而非只按 `sessionId`）？**  
> 防止下午调试同一问题时连开 3 个新会话读同一篇冷文档，在两小时内把它从 `20` 刷到 `70+` 触发误恢复；真正跨天、跨周的再次使用才符合“持续活跃”。

### 4.3 精简后的四个操作等级（去掉空转分段）

| 温度区间        | 等级     | 实际行为与调度语义                                                                                                                       |
| --------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| $T \ge 50$      | `active` | 正常在 L1（或活跃 Group）中暴露。其中组内若长期满足 $T \ge 75$ 且 $S \ge 60$ 天，可作为 `pinned` 快速入口建议候选                        |
| $25 \le T < 50$ | `cool`   | 观察与建议区：仍保留默认索引；`suggest` 模式下进入候选清单（按「温度低 + L1 字符占用高 / 未归组」优先排序）                              |
| $10 \le T < 25$ | `cold`   | 达到冷却线；若满足 `historical` + 非 `pinned` + 通过最小保护期，在 `auto` 模式下自动设置 `archivedAt`（`archiveOrigin="auto-inactive"`） |
| $0 \le T < 10$  | `frozen` | 深度冷区；与 `cold` 同样处于归档状态，但在 `memory_search` 中带更低的状态权重                                                            |

**回差（Hysteresis）防抖动**：

- 进入自动冷却：$T < 25$；
- 自动恢复：$T \ge 50$（且仅限 `archiveOrigin === "auto-inactive"`）。
- 一次冷读从 $T = 15$ 升到 $15 + 0.35 \times 85 \approx 44.75$，**不会单凭一次误点开立刻恢复**；若隔过冷却窗口后再次需要并读取，升至 $44.75 + 0.35 \times 55.25 \approx 64.1 \ge 50$，自然完成唤醒（或在读取后顺手 `topic_append` 更新，直接上 85 唤醒）。

### 4.4 Group 温度规则（消除冗余状态）

Group **不单独跑一套易失真脱离成员的衰减曲线**：

- **非空组（存在至少 1 条活跃成员）**：Group 有效温度 $= \max(\text{组内活跃成员的 } T)$。只要任意成员仍热（即使成员走 `pinned` 或 `memory_search` 直读未翻目录），Group 就保持活跃；**当且仅当组内全部活跃普通成员均已冷却时**，下一轮评估才将 Group 整体自动冷却（若组内有 `standing` 或 `pinned` 活跃成员，则永不冷却该 Group）。
- **空组（建组后尚未挂成员，或成员已全部归档）**：以最近一次目录访问 / 建组 / 成员迁出时间为锚点，按默认 $S_0 = 30$ 天衰减，低于 `25` 且非 `standing` 时自动退出 L1。

### 4.5 `memory_search` 与 `frozen` 的协同修正

修掉当前 `src/service/index.mjs` 把全部归档 Topic 强行 `score: 0` 的问题：

- 归档 Topic 仍保留完整的词法命中分 `lexicalScore`（避免精确命中的深度冷文档被模糊命中的较新冷文档掩盖）；
- 排序综合分：`finalScore = lexicalScore * stateWeight`，参考权重：
  - 活跃 Topic：`1.0`
  - `cold` 归档 Topic：`0.75`
  - `frozen` 归档 Topic：`0.50`
- 结果仍明确标注 `state: "archived"`（可选附带冷度提示供面板展示），**不返回正文**，保持冷检索契约不变。

## 5. 自动冷却与恢复护栏

### 5.1 Topic 自动冷却护栏（全部为真才执行）

```text
autoCoolTopic =
  effectiveRetention === "historical"            // Topic 显式值 ?? 主 Group 默认值 ?? "standing"
  && !pinned
  && !archivedAt                                 // 当前活跃
  && ageSinceCreatedOrEdited >= minCooldownDays  // 建议初始 30 天
  && ageSinceManualRestore >= minRestoreGraceDays // 建议初始 14 天，防止刚手恢复又被冷掉
  && T < 25
  && statsValid                                  // statsStartedAt 存在且观察期达标、账本未损坏
  && !clockRollback                              // now >= 事件最大时间戳
```

### 5.2 Topic 自动恢复护栏

```text
autoRestoreTopic =
  archivedAt !== undefined
  && archiveOrigin === "auto-inactive"           // 手动归档永不自动恢复
  && T >= 50
  && !clockRollback
```

### 5.3 Group 自动冷却护栏

- 必须**先冷却符合条件的组内 Topic，下一评估周期再评估 Group**（不跨层级单轮级联）；
- 满足：无 `standing` 活跃成员、无 `pinned` 活跃成员、无剩余活跃普通成员（或空组已超过冷却阈值）、且 Group 自身 `retention === "historical"`、无时钟回拨与统计异常。

## 6. 事件存储、跨作用域统计与失败语义

### 6.1 存储位置（`stateRoot`）

在 `stateRoot` 新增轻量事件日志（按 **Topic/Group 的真实物理 `targetScopeId`** 存放，例如 `global` 与 `amber` 各自独立账本）：

- **路径建议**：`<stateRoot>/topic-activity/<hex(targetScopeId)>.json`
- **结构**：`statsStartedAt`（首次启用统计时间）、`events[]`（`type`, `targetKind: "topic"|"group"`, `key`, `at`, `sessionId`, `extra?`）、`checkpoints`（事件过多时压缩保留 `{ T, S, lastHeatedAt, lastUpdatedAt, statsAnchor }`）。
- **绝不保存对话正文**；**按真实物理归属统计**——例如在 `amber` 会话里读取了 `global` 的 Topic，该 `read` 事件记入 `global` 账本，防止单一人设长期不用时误冷全局共享记忆。

### 6.2 并发与只读宿主（F7 Seat / Shadow）兼容

- **读工具并发安全**：`memory_read` 与 `memory_search` 在 `controller.mjs` 中是并发安全（`isConcurrencySafe: true`）的读路径，**统计落盘必须异步缓冲 / 节流写入且失败不阻塞返回**（参考 `state.mjs` 的 `waterlineStore` 模式，不在每次读请求上同步抢锁阻塞主回答）。
- **只读宿主（`HOST_LOCKED`）与 Shadow 模式**：
  - `shadow` 模式不写任何统计（严格沿用现有只读契约）；
  - 第二宿主处于 `HOST_LOCKED`（只读态）时，跳过统计写入或在锁冲突时静默丢弃遥测，绝不因记一条热度导致 `LOCK_BUSY`。
- **失败安全（Fail-Closed for Auto-Cooling）**：
  - 统计文件损坏、缺失 `statsStartedAt`、或检测到时钟回拨（`now < maxEventAt`）时：**正常记忆读写零影响，自动冷却直接熔断停用并上报诊断**。

### 6.3 存量冷启动规则

- 上线后记录统一的 `statsStartedAt`；
- 存量 Topic 缺省 `retention = "standing"`（天然免疫自动冷却）；
- 对于用户后续标为 `historical` 的存量 Topic：若缺失读取记录，按最后内容写入时间折算种子温度 `T0 = 100 · 2^(−N/S0)`（`N` = 距 `updated` 的天数，`S0` 默认 30；缺 `updated` 时回落 `T0 = 50`），并给足初始观察期（`now - statsStartedAt >= minCooldownDays`，默认 30 天），杜绝上线即批量误冷；
- 种子温度的 `reason` 固定写「存量种子：最后更新于 N 天前，种子 T=x」，面板可解释；
- 已知风险：`updated` 不反映读取，只读不写的文档会被判冷；观察期内的真实 `read` 会加热（12.5 → 43.1，可再撑约 24 天），且冷却可逆。

## 7. 自动化分级与执行契约

提供三档模式（复用现有 `settings` 与 `management` 通路）：

- `off`：仅记录活动与指标，不产生整理/冷却建议；
- `suggest`（**首个实现版本默认**）：纯只读计算温度、生成冷却/恢复/`pinned`/拆分候选，由面板预览确认；
- `auto`：在面板显式开启后，自动执行符合全部护栏的**可逆冷却与恢复**。

**执行安全规范**：

- 复用现有 `service.mutate`（CAS + `journal` + `operationId` 幂等）与每轮批量上限（如 `20` 条）；
- **L1 水位压力只能触发分析提示，绝不动态缩短 $S$ 或降低冷却阈值**（禁止“恐慌性遗忘”）；
- 拆篇、合并、改写正文、修改 `retention` / `pinned`、删组迁移等有损或结构性变更，**永远只走 `queue → previewPlan → executePlan` 预览确认，不进 `auto`**。

## 8. 评价指标与测试重点

### 8.1 核心观察指标

- **误冷率与冷后后悔率**：冷却后短期内（如 14 天）又被 `memory_search` 捞回读取的比例；
- **索引失真率**：`search_hit` 高但 `read` 极低的 Topic（用于定位需要重写 `summary` 的索引）；
- **L1 占用与单篇读取成本**：L1 总字符数变化、长文档拆分后的单次阅读字符量变化；
- **抖动次数**：同一 Topic 反复冷却 / 恢复的次数。

### 8.2 纯函数与集成测试重点

- 温度引擎保持纯函数（显式注入 `now` 与参数），覆盖：
  - 25 / 50 回差边界与防抖动；
  - 间隔巩固 $S$ 增长与 $S_{\max}$ 封顶（满温连刷几乎不涨 vs 低温暖召回明显涨）；
  - 渐近饱和加热 $\alpha(100 - T)$；
  - 全局时间冷却窗口去重（同日跨会话连刷不误恢复）；
  - `search_hit` 不加热、`group_list` 不给成员加热；
  - `standing / pinned / manual` 护栏与 30 天最小保护期；
  - `global` Topic 跨人设读取归集到 `global` 账本；
  - 父 Group 冷却时子 Topic 自动恢复的闭环可见性；
  - 时钟回拨 / 统计损坏熔断；只读宿主不触发 `LOCK_BUSY`。

## 11. 0.5 功能修正与自动整理

> 2026-11-21 木偶人现场提出，本节先记录缺陷与方案，拍板后进阶段 A/B/C 施工。

### 11.1 Spark 卡片写入后不建向量（语义召回对新卡失效）

**现象（实测）**：新增 spark 卡片后，语义召回搜不到这张新卡；只有字面 trigger 命中才会被投递。

**根因（2026-11-21 源码核对）**：

- 向量只在 `runSemanticRebuild`（`src/plugin/controller.mjs:520` 起）里建立，其调用点只有两处：手动 `semantic_rebuild` 工具与下载模型后的 `triggerAutoRebuildAfterDownload`（`force:true`）。
- `spark_save` / `spark_update` / `spark_forget` 的写路径**完全没有向量维护钩子**。
- 召回侧 `src/sparks/semantic-recall.mjs:169` 的判据是 `entry === null || entry.revision !== card.revision` 就 `continue`（注释写着「缺失/过期：重建负责」），而并没有自动重建兜底——于是新卡与改过的卡永久落选语义补位。
- 影响面：语义召回只对「上一次手动重建时已存在」的卡有效；之后新增的卡全部失效，`spark_update` 改过内容的卡旧向量过期后同样被跳过。0.4 的 F1b 语义召回是半可用状态。

**修法（三层）**：

1. **写后增量（主路径）**：`spark_save` / `spark_update` 成功提交后，把 `{id, revision, cardEmbedText(record)}` 投进后台增量队列（单飞 + 防抖若干百毫秒），批量 `embed` → `store.upsert` → `store.save()`；`spark_forget`（archive / supersede）成功后 `store.remove(id)` 并落盘。绝不阻塞工具返回，失败静默重试一次后由下一层兜底。
2. **启动差集补齐（兜底）**：拿 active 卡集合与索引条目比对 revision 集合，不一致的卡后台走增量重建（复用 `runSemanticRebuild` 的非 force 路径，未变卡直接沿用）；顺带 `retainOnly` 剔除已删卡残留。
3. **手动 rebuild 保留**：换模型 / 维度变化仍走 `force:true` 全量。
4. **并发防线（必须）**：写后增量队列与 `runSemanticRebuild` 共用同一个 scope 级单飞锁。`src/semantic/store.mjs` 是内存 Map + 整文件 `atomicReplace`，无文件锁；`controller.mjs:534` 在 `force:true` 时直接 `store.clear()`。若增量 `upsert` 与全量重建的 `clear()` / `retainOnly`（用重建开始前的旧快照）交错，会覆盖新卡或误删向量。重建进行中，增量任务只标 dirty，等重建收尾后按差集补一次（复用第一层逻辑），绝不与重建并行写盘。

**验收方式**：

- 新建卡、不点重建，下一次含转述表述的对话能靠语义被召回（构造只改变说法、不命中 trigger 的用例）；
- `spark_update` 改正文后，新内容可召回、旧向量不再命中；
- `spark_forget` 后索引无残留条目；
- provider 不可用 / 模型未装时：写路径零报错、召回退回纯字面，诊断可见；
- `npm test` 全绿，既有 sparks / semantic 用例断言零删改。

### 11.2 自动记忆整理：调度、执行与遗忘边界（2026-11-21 拍板）

先把两条链路分清，后面开发不许再把它们搅在一起：

- **整理（Topic 冷热）**：0.4 已有的 `archivedAt` 语义，0.5 换一套更懂事的判据（温度模型）。只管「这条 Topic 该不该继续占 L1、该不该进冷检索」，可逆。
- **遗忘（Spark 衰减）**：0.4 已有的 60 天衰减 + `archiveScore`，按 `useCount` 续期，**不归温度调度管**。0.5 只补它的诊断与触发器整理（§11.3 / §11.4），不重做衰减公式。

两者在面板上并排展示「Topic 冷区 / Spark 冷区」，但计算与执行各走各的路，不互相触发、不共享阈值。

#### 11.2.1 触发：什么时候跑一次评估

三个入口，按优先级：

1. **每 24 小时一次（主入口）**：距上次成功评估满 24 小时后的第一次人类会话触发。人类判据是 pre-step 拿到的本轮上下文里存在 `source.kind === "user"` 的消息——这是心跳插件 `turnOriginIsUserSplice`（`dsh-heartbeat-v2/src/statusbar/time-inject.ts:58-69`）同一套口径。心跳投递的 source 不是 `user`，所以引擎室轮次天然跳过；「每天第一次对话」的写法不用了，因为它会撞心跳首跳、把整理跑进引擎室。满 24 小时没人类会话就一直等，不按时钟硬跑。
2. **L1 软水位（辅助）**：渲染时发现 L1 总字符逼近 `softChars = 9800`，就在下一次人类轮次的 pre-step 顺带评估一次。**水位只触发分析，绝不缩短 `S`、绝不降低冷却阈值**（§7 安全规范，禁止恐慌性遗忘）。
3. **手动**：面板「立即评估」按钮与调试用工具调用，任何时候可跑，只在 `suggest` 模式或预览里生效，不直接写盘。

不做的：不在定时器 tick 上跑（会与心跳、后台任务抢写）；不做「宿主空闲判定」（判定本身不可靠，代价大于收益）；不做每次工具调用后即时评估。

#### 11.2.2 评估：一次评估到底算什么

评估是**纯函数回放**，零写盘（除了 §6 的事件账本自身），输入只有三样：

- `<stateRoot>/topic-activity/<hex(scopeId)>.json` 的事件流（read / updated / search_hit / group_list / manual_restored）；
- `topics/*.md` 的 frontmatter（`retention` / `pinned` / `archivedAt` / `archiveOrigin` / createdAt / updated）；
- `groups.json` 的结构与成员关系。

输出每条 Topic 的 `(T, S, tier, reason, alarms)` 与每个 Group 的有效温度（= 组内活跃成员 T 的最大值，§4.4）：

1. 按事件时间顺序回放，每次 heated 事件先按 `T \cdot 2^{-\Delta t/S}` 衰减到事件时刻，再应用加热（read 用 `\alpha = 0.35`，updated 用 `T = max(T, 85)`）与间隔巩固 `S`；`search_hit` 与 `group_list` 不加热。
2. 回放到 `now`，得到当前 `T` 与 `S`。
3. 按四档归类：`T >= 50` active、`25 <= T < 50` cool、`10 <= T < 25` cold、`T < 10` frozen。
4. 对每一条算出「为什么是这个档」的 reason（最后一次有效使用距今天数、S 当前值、是否撞到护栏），供面板解释。**没有 reason 的自动决策一律不许执行。**

#### 11.2.3 执行：三档模式各自做到哪一步

沿用 §7 的模式开关，默认 `suggest`：

- **off**：只记账本，不算温度、不出建议。适合排查期。
- **suggest（默认）**：算出全部候选，面板列出「建议冷却 / 建议恢复 / 建议 pinned / 建议拆篇」四张清单，每条带 reason 与影响字符数；用户点确认才执行，执行走 `previewPlan → executePlan`。
- **auto**：面板显式开启后，只自动执行**可逆且无结构变更**的两类：`archive-topic`（写 `archivedAt` + `archiveOrigin="auto-inactive"`）与 `unarchive-topic`（清 `archivedAt`）。每轮上限 20 条，单条 CAS + `operationId`，写审计事件，面板可一键撤销本轮。

**永远不进 auto 的四类**（无论模式）：拆篇、合并、改写正文、改 `retention` / `pinned` / 删组迁移。这些是结构性或有损变更，只能走 `queue → previewPlan → executePlan` 人工确认（§7）。

auto 的完整准入条件就是 §5 的两段护栏，逐条真才执行：`retention === "historical"`、非 `pinned`、当前活跃、创建/编辑满 `minCooldownDays = 30` 天、手动恢复满 `minRestoreGraceDays = 14` 天、`T < 25`、`statsValid`、无时钟回拨；恢复侧再加 `archiveOrigin === "auto-inactive"` 且 `T >= 50`。

#### 11.2.4 失败语义与熔断

- 账本损坏、缺 `statsStartedAt`、检测到 `now < maxEventAt`（时钟回拨）：正常读写零影响，**自动整理直接熔断停用**，面板显示诊断，等用户处理。
- 只读宿主（`HOST_LOCKED`）与 `shadow` 模式：不写统计、不执行 auto，评估结果只读展示。
- 评估本身超时（大账本回放慢）：本次放弃，记诊断，不影响对话；下一轮再试。

#### 11.2.5 与 Spark 遗忘的边界（再写一遍，防漂移）

- Spark 的生死还是 `score = 2^{-elapsedDays/halfLifeDays}`、`halfLifeDays = min(base \cdot 2^{useCount}, max)`（base 30 / max 240）、60 天硬冷却 + `score < 0.25`，只有 `spark_feedback(used:true)` 续期——这套不动。
- Topic 的温度不读 Spark 的 score，Spark 的衰减不看 Topic 的 `T`；两套事件账本也不合并（Topic 在 `stateRoot/topic-activity`，Spark 在 `sparks.jsonl` 自身字段）。
- 唯一的交叉点在 UI：面板把两边冷区并排列出来，让用户一眼看到「哪些 Topic 冷了、哪些卡快被忘了」，但点「恢复」各自走各自的操作。

#### 11.2.6 热度参数做成可配置项（面板可改）

温度公式里的数字不许写死在代码里，全部落 `settings`，面板「设置 → 记忆整理」给一组表单。默认值与建议范围：

| 参数                  | 含义                              | 默认   | 范围    |
| --------------------- | --------------------------------- | ------ | ------- |
| `s0Days`              | 新生 Topic 的初始有效半衰期 $S_0$ | 30 天  | 7–90    |
| `sMaxDays`            | 巩固上限 $S_{\max}$               | 180 天 | 60–365  |
| `consolidateGain`     | 间隔巩固增益 $g$                  | 0.5    | 0–1     |
| `readAlpha`           | `read` 加热系数 $\alpha$          | 0.35   | 0.1–0.6 |
| `updatedFloor`        | 内容修改后的温度保底              | 85     | 50–100  |
| `readDedupHours`      | `read` 全局冷却窗口（去重）       | 24h    | 6–72    |
| `coolThreshold`       | 冷却线，低于即 `cold`             | 25     | 10–40   |
| `restoreThreshold`    | 恢复线，回升到即恢复              | 50     | 30–80   |
| `minCooldownDays`     | 最小冷却年龄                      | 30 天  | 7–90    |
| `minRestoreGraceDays` | 手动恢复后的保护期                | 14 天  | 3–30    |
| `maxOpsPerRun`        | `auto` 单轮最多执行条数           | 20     | 1–50    |
| `evaluateEveryHours`  | 评估周期                          | 24h    | 6–168   |

**UI 行为纪律**：

1. **先预览后应用**：改任一参数只进入「预览」态，用新参数对全量 Topic 重算一遍温度，只读展示「若生效，哪些会冷却 / 哪些会恢复 / L1 字符净变化」，用户确认后才写 `settings`。
2. **校验前置**：`sMaxDays > s0Days`、`restoreThreshold >= coolThreshold + 10`（回差）、`minRestoreGraceDays <= minCooldownDays`；非法值当场拒绝并说明原因，不静默夹取。
3. **执行层延迟，计算层不回溯**：温度计算坚持纯函数事件重放（§11.2.2），所以预览算出的 T 与下一次评估算出的 T 必须一致——改参数后它**一定会**用新参数重算全部历史事件，这是可回放模型的本意。真正要防的「手一滑当场批量误冷」由执行层挡住：保存参数只是一个 settings 提交，**当刻不触发任何 auto 执行**，留到下一次正常评估周期（或预览里手动确认）才生效，且仍受每轮 20 条上限与一键撤销保护；也不补执行「过去本该执行」的动作。
4. **可对照**：面板显示「当前值 / 默认值」，一键恢复默认；每次参数变更记一条审计事件（时间、旧值、新值），可在状态页查到。
5. 参数变更不影响 Spark 衰减那套常量（`base` / `max` / `archiveScore` 是 Spark 自己的配置项，落在另一组设置里，§11.2.5 已划清边界）。

**已拍板（2026-11-21，m00523）**：

1. 评估周期按「距上次成功评估满 24 小时」，不按自然日。
2. `auto` 首版就做，默认走 `suggest`，面板里手动打开才生效；每轮 20 条上限 + 一键撤销必须同时具备。
3. 面板状态页显示「上次评估时间 + 下次触发条件」，与 L1 水位、冷热分布放同一页。

#### 11.2.7 整理向导（首启引导，产品化迁移）

温度引擎与 Group 折叠都依赖「用户已经把记忆分好组、标好 retention」，但第三方用户不知道要迁移。因此不写一次性迁移脚本，交付一个向导：

### 11.3 Spark 自动分组、自动连线与取消连线

**现状（2026-11-21 源码核对）**：

- 图谱「簇」是派生视图，规则只有一条：`entities[0]`（`src/sparks/graph.mjs:285-310` 的 `clusterKeyOfNode`），没有主实体的卡统一落 `__unclustered__`「未分类」。同一个实体几种写法各成一簇，长此以往「未分类」越堆越大，分组观感自然差。
- 连线只有 `links` 字段，完全靠模型在 `spark_save` / `spark_update` 时手填；工具层没有单条增删接口，改一条边要整组替换。
- level 2 簇内视图只输出簇内节点与边，跨簇的 link 在面板上看不到。

**需求**：自动分组、自动连线、能取消连线；跨组连线要可见。

**方案**：

1. **实体规范化**：建别名表（大小写、全半角、常见同义写法归并），投影前先归一再分簇；这是零风险的第一步，先解决「同一实体散落多簇」。
2. **自动归组**：保存/更新后按语义向量找最近的已有簇（以各簇代表卡的向量均值或主实体名向量比较），相似度过阈值即归入，未过则维持主实体分簇；不新增不可逆字段，先保持派生；簇规则版本号 `clustersVersion` 放配置，规则升级后全量重算；人工覆盖走 sidecar `dataRoot/spark-clusters.json`（只存被改过的 `cardId → 簇名`，读取时覆盖派生结果），卡片本体不动、不做迁移。
3. **自动连线（方案 2：参与 1 跳投递，只挂新卡自身）**：`spark_save` / `spark_update` 提交时，取与当前卡相似的 top-k（相似度阈值 + 每卡上限 + 去重），把 `auto:similar` 边**只写进当前卡自身的 `links`**，绝不反向修改老卡。写入与卡内容在**同一次 `mutate`** 里完成，Agent 拿到的 revision 就是最终值，不会事后被后台任务顶掉；向量查询失败或 provider 不可用就跳过本次自动连线，**不做异步补写**（避免 CAS 冲突与 `seen` 冷却键重置）。`src/sparks/match.mjs` 的 1 跳扩散会把 auto 边当普通 related 投递（`maxRelated` 默认 2）——这是明确接受的代价：用户聊到新卡时会带出它连到的老卡，反向不带出。人工边与 auto 边分开管理：保留 `spark_link` / `spark_unlink` 细粒度工具，面板可一键清理 `auto:` 前缀边。起手阈值 `0.80`、每卡上限 `3`；相似度分存独立字段（不塞进 `rel`）；定稿前用 47 张卡两两 1081 对标定 top 30。
4. **取消连线**：`auto:` 前缀的边可一键清理（面板「清理自动连线」）；人工写的 `rel` 不动。`spark_forget` 归档时自动清理指向它的边并落盘。
5. **跨簇边渲染**：level 2 输出 edges 时保留指向簇外的边，客户端把外部端点画成小标记（点击可跳到对应簇），不再静默丢弃。

**已拍板（2026-11-21）**：

1. **分组不落 spark schema**：0.5 走纯派生，簇规则版本号 `clustersVersion` 放配置，规则升级后全量重算；人工覆盖走 sidecar `dataRoot/spark-clusters.json`（只存被改过的 `cardId → 簇名`，读取时覆盖派生结果），卡片本体不动、不做迁移。

### 11.4 Spark 投递率诊断与关键词整理

**现状**：

- `hitCount` / `lastHitAt` 只在投递成功后 +1（`src/sparks/store.mjs:1496-1497`），没有任何「未命中」记录。
- 召回诊断只有全局数：`diagnostics.semantic` 的 `candidates` / `error`，看不到「某张卡为什么没有出现」。
- 因此无法回答用户的问题：一张卡没触发，是那段时间根本没聊到，还是聊到了但字面与语义都没识别出来。

**需求**：弄清未触发归因；给高频投递的卡降噪；定期整理触发器与实体。

**方案**：

1. **召回诊断账本**（stateRoot，轻量、按 7 天滚动）：每轮 pre-step 记一条不含正文的记录——时间、scope、`literalHits`、`semanticCandidates`（最高分 + 分布）、投递的卡 id 列表、落选原因聚合（字面未中 / 语义分低于阈值 / seenKeys 冷却 / 种子槽已满）。
2. **每卡覆盖率统计**：最近 N 天的投递次数、used 次数、最后命中时间；输出「从未投递」与「高频投递但低使用」两个清单。
3. **归因**：从未投递的卡分两类——该 scope 期间无有效召回轮次（没聊）与有轮次但分数始终低于阈值（识别不到）；后者用最高语义分证明，前者用轮次计数证明。
4. **整理建议（suggest，人工确认后写回）**：高频低用 → 剔除泛化触发器；从未投递 → 补触发器 / 补实体 / 合并相近卡；重复投递 → 向量相似度找同主题卡，建议 `supersede` 合并。
5. **面板**：图谱节点悬浮显示投递次数与上次命中；新增「投递体检」页签，列上述两个清单与建议操作，一键生成 `spark_update` 补丁。

### 11.5 聊天消息下的「闪回命中」按钮（体验与关联精度的返工）

**现状（2026-11-21 源码核对）**：

- 按钮实现见 `client/index.js:6861-6930` 的 `FlashbackActions`：每个 assistant 消息动作区一个朴素按钮，点开是浮层，列出「本会话最近一次投递（10 分钟内）」的卡片、命中的触发词与来源（seed / related）。
- 之所以只做「10 分钟近似」：宿主插槽只给消息 `messageId`，而投递是独立 context 消息（`source` 带 deliveryId/sparkIds），客户端建立不了「这条回复 ↔ 那次投递」的映射，于是如实降级成按会话时间窗匹配（`client/index.js:6839-6860` 的注释写明）。
- 结果是：同一次投递会在该会话所有消息下重复出现；没有反馈入口、没有「为什么是这几张」，信息量约等于无。这就是「只提醒 10 分钟内投递了，没用」的来源。

**修法**：

1. **服务端补轮次关联（服务端已具备，卡点在客户端）**：pre-step 处理器本来就能拿到 `fresh[0].id`，`recordPending` 也已经把 `sourceMessageId: fresh[0].id` 写进投递记录（`controller.mjs:1482`、`:1533`）。所以服务端只需把它投影进 `getGraph` 的 `deliveries[]`（字段名 `turnRef` / `sourceMessageId` 二选一，与现有记录对齐），客户端优先按它精确匹配，旧记录无该字段时回落 10 分钟窗口。真正要核实的是客户端侧：`conversation.chat.assistant-actions` 的插槽 props 只有 assistant 消息的 `messageId`，要看宿主前端是否附带 `parentId` / `turnId` / `replyTo`，或能否用会话消息列表反推出上一条 user 消息 id。
2. **按钮改形态**：消息动作区一个线稿图标 + 数字徽标（本轮投递 N 张时显示「N」），无投递则不占位；配色沿用侧边栏图标同一套 stroke/currentColor。
3. **浮层重做**：卡片式列表，每张卡显示标题、摘要一行、命中触发词、来源、语义相似分（语义命中时）；每张卡两个动作——「有用」`spark_feedback(used:true)`、「没用」`used:false`；点卡片标题跳到图谱对应节点。底部一行汇总「本轮 N 张 / 触发词命中 x / 语义补位 y」。
4. **反馈闭环**：used 反馈直接进入 §11.4 的投递统计，高频命中但不 used 的卡在整理建议里降权，形成「命中 → 反馈 → 整理」闭环。
5. **样式纪律**：浮层与面板同一套视觉（圆角、细边、阴影、等宽数字），不新增第二个按钮家族；按钮文案从「闪回命中」改为更直白的「闪回 N」，避免与面板页签同名混淆。

**待拍板**：无投递时是完全不显示，还是显示灰度图标（可点开看「本轮最接近但未达阈值的卡」，用于诊断）？

**已知 UI 缺陷（2026-11-21 用户实测，m00455 / m00459）**：按钮不点开时与复制 / 好回答 / 坏回答同一水平高度，点开后按钮跳到上一行。现有样式里 `.dshi_fbWrap` 是 `position:relative;display:inline-flex`、`.dshi_fbPop` 是 `position:absolute;right:0;bottom:calc(100% + 6px)`（`client/shiori.css:87-88`，内联副本在 `client/index.js:126-127`）——按设计绝对定位不该撑高容器。实际跳动说明浮层在这条插槽里参与了布局（样式未作用到该插槽节点，或被宿主容器样式覆盖），`.dshi_fbWrap` 高度从「按钮」变成「按钮 + 浮层」，动作条把整块换行顶到上一排。修法：浮层改 `position:fixed` + `getBoundingClientRect()` 定位（或 portal 到 body），彻底脱离宿主容器布局；组件样式全部改 React 内联 `style`，不依赖 className 注入；按钮固定 `min-height`，开合前后尺寸不变；补一条回归测试断言「开合前后按钮 `offsetTop` 不变」。

### 12.3 渐进式工具加载：暂不做（本次拍板）

**结论**：0.5 不做工具级的按需加载，19 个工具维持全量注册（9 兼容 + topic_create + group_manage + 8 Spark，含 spark_link / spark_unlink；口径见 §12.4）。

**理由**：

1. DSH 没有原生的按工具延迟加载机制。工具面在会话启动时确定，中途改注册表会让 KV 前缀从变化处失效（`dsh-toolsets` 记录：可见 schema 集合与顺序必须稳定）。
2. 插件侧虽然能靠 `tools.register` 返回的 disposer 动态注销、再注册，但模型看到的工具清单一旦不完整，「有个加载器可以拉出更多工具」这件事很难被主动想到——尤其 `spark_save` 正是要对抗「不想写」的工具，藏起来只会更没人用。
3. 成本大头是每轮请求都要携带的描述文本，不是调用频次。折叠低频工具省下的 schema 有限，却要改 CONTRACTS、验收用例与工具面稳定性。
4. 真要做也有替代路径：描述瘦身（低风险、一次到位）与低频工具合并（如 `spark_forget` / `spark_feedback` / `group_manage` 并入一个 `shiori_admin(action=...)` 入口，19 → 17）。后者动契约，列入 0.6 候选，不进 0.5。
