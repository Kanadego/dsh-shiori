4. 渲染开工卡：`node D:/AIagent/tools/make-card.mjs --subtask <id> --data <json> --out card.md`。**`requirements` 必须是字符串**（数组会被渲染成逗号一行）；渲染后必读一遍，检查卡里有没有「禁止改测试 vs 允许同步断言」这类自相矛盾。

**验收（每张子单）**

1. worker submit → `take-test`（tester）→ **全量** `npm test`（worker 只跑白名单测试文件）。
2. `verify-packet`：只看 `mismatched` / `missing`，都为才往下（extra 是未改文件，正常）。
3. `test-accept` 写报告（tests/pass/fail 原文）。
4. `start-review` → 派**独立交叉审查子代理**（一单一个，不能自己审了就跳）。审查必须做**变异测试**：对新增/改动的守卫与断言挑 2–3 条关键判据，把实现或调用点临时改坏，证明用例真的会红，再原样恢复（`git status` 必须回到提交态）；只跑绿不算过。审查结论到手前 `crossReviewed` 只能填 false——**没做交叉审查绝不许在 accept 或工作台里填已审**，假报比漏审更严重。
5. `accept` 六旗标：`--ck-self --ck-cross --ck-touched --ck-debt --ck-debt-next --ck-merge`（`--ck-debt true` 要 `--debt-note-file`）。
6. 合并：`cp -f` 白名单文件到主仓 → 去掉仓库自带的 CRLF 噪声（`git diff --stat` 与 `-w --stat` 数字应一致）→ 全量 `npm test` → `git add` **显式列文件** → commit。跨线重叠文件用 `git merge-file`，base 取两线共同祖先。
7. 收尾：账本勾掉、`shiori-dev` topic 追加、§9.2 更新、债务写进下一轮。

**打回（最容易用错的三个）**

- 状态 `testing` 时不能 `rework`（E_STATE）——先 `take-test` 再 `test-fail --reason-file`。
- `--items-file` 必须是**纯数组**，每项 `{id, severity: "high"|"medium"|"low", file, expected}`。
- 报告用 `--report <路径>`（没有 `--report-file`）。**格式错时工作台只打用法说明、不会真发出**——看到用法说明就核 board 状态，别以为打回成功。

## 7. 硬规矩（踩过的坑，不许再踩）

- 只审不写：审查员不下场改业务代码，打回走结构化 items；要自己动手先用 update-roles 摘掉 reviewer。
- 白名单纪律：worker 只碰白名单；审查员要放行新文件用 `update-whitelist --add` 并写理由（本次为跨线断言、liveRefs、审计 kind 各加过一次）。
- 断言不许放宽：授权内的改动逐条写理由；「零非 getStatus 调用」这类判据要按方法名放行，不许改成「任意调用都行」。
- 数字一律现取：报告里的 numstat / 通过数用命令现跑，别凭记忆写（这次我把 +11/−7 记成 +9/−6，被审查员当场质疑）。
- 冻结快照 ≠ 当前值：任何「服务端拿 settings 与提交值比对」的设计，先确认该设置是否在 liveRefs；不在就必须先接进去，否则保存链路必挂。
- 事实纪律：可验证的东西（版本、行号、计数）不凭语境推断，不确定就说「不确定」。
- 交叉审查是红线，不许跳过、不许假报：每张子单必须有独立交叉审查结论（含变异测试记录）才能 `--ck-cross true`；没审填 true 等于造假账，一旦发现整批验收作废重来。
- watcher 常驻：派单后立刻挂 `node D:/AIagent/out/wb-watch.mjs`；它遇 submit / ask-question / request-whitelist / test-fail 就退出，**处理完任一事件第一件事是重挂**。每跳开始前 `job_list` 确认恰好一个在跑，0 个补挂、多于 1 个先 kill 多余的。

## 10. 教训（给自己看）

1. 自查通过数证明不了守卫存在，判据要能「删实现会红」——本轮 B 线两次打回都是因为断言恒真或只拦旧字面量。
2. 交叉审查必须一单一个，而且必须点名要做变异测试；但它不必每次重审全盘，同一子代理做定点复核（「这几条闭合了没」）更快也准。
3. 用户可见的假话比崩溃更坏：三轮打回里四条是「没落账说落了 / 落了说没落 / 错因归因 / 换文案就静默失效」。凡是要展示给用户的状态，都要有可验证的回执字段支撑。
4. 方案与文档也可能是错的（计划写 21 个工具实际 17），以代码为准；但既然要写口径，就把代码里那些反向注释一起清掉。
5. 批次收口就立刻准备下一批的线与卡，别停在「等指示」。
6. 变异测试是防「假绿」的唯一硬手段：用例全绿只证明它没崩，改坏实现还绿就说明守卫是假的。交叉审查不收变异测试记录 = 没审。
7. 没挂 watcher 等于没在现场：worker 提问和提交不会等人，漏看一次就可能把整条线卡在原地。watcher 偶发静默退出（exit 0、无 HIT），兜底必须靠 board/inbox 轮询，别把 watcher 当唯一信号。
8. 打回要打回到根：5A 第二次打回里两条 —— 范围越界（只加空行、放宽计时）和守卫不可达（requireActive 被上层的 requireActiveDataAccess 先抛）——都不是「测试不够」，而是实现里多了不该有的东西、和假的防线。修法要删冗余而不是补断言。
9. 临时放宽的断言必须单独记账：5A attempt 2 把四处计时阈值放宽到 10s，理由是「消除 flaky」，实际换回原值仍全绿。凡是改既有断言阈值的，都要附上换回后仍绿的证据。
10. 5D 的教训是「回归断言要钉在被改的那个属性上」：浮层改回 absolute 时，用浮层内按钮的 offsetTop 断言是恒真的，必须用主按钮引用/aria-label 定位到插槽按钮。
