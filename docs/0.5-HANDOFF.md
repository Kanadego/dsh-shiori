## 10. 教训（给自己看）

1. 用例全绿只证明它没崩；改坏实现还绿就说明守卫是假的。交叉审查不收变异记录 = 没审。
2. 交叉审查的裁决要按**开工卡原文**复核：批次 10 两次首判 accept 都被我按卡面「每条至少一次变异验红」要求重新裁决，改判 rework 后才补上真正的守卫（schema 静态断言、实参 spy、readGroups realpath 精确断言）。子代理会心软，裁量权在我。
3. 合并是事故高发段：`git merge-file` 参数顺序错会**静默吞改动**（不是冲突）；`cp` 脚本漏写一棵树也不报错。合并后必须全量跑 + 逐文件核 `git status`，别信「三方合并 0 冲突」。
4. 事件门控要么等真正的收场信号，要么等于没等：批次 9 的 `awaitStartupSync` 等的是 startupSyncs，而新卡走的是后面的 flush，门控 26ms 就过去了。
5. 工作台的状态会滞后于我的直觉：`subtask` 还显示 testing、租赁已交还，先 `take-test` 看响应码再判断。
6. 判据要钉在被改的那个属性上：批次 7 的 `waitForAutoState` 用文件存在性做门控，在并行负载下必飘；换成诊断计数后才稳。
7. 每次验收完立刻把债写进本文件 §9 与 `shiori-dev` topic，别攒——批次 8 的债攒到 9、9 攒到 10，最后得开一轮专项清。
8. 木偶人看的是「有没有凭证」：ck-cross 只是我勾的框，报告 JSON 才是凭证。
