# dsh-shiori v0.2.1

**「候选 / 计划」页改版为「整理与遗忘」：候选分组折叠、状态筛选、就地预览、人话错误，并修掉三个让人卡住的问题。**

0.2.0 让记忆能想起来；这一版收拾的是**用起来**：整理页以前把 25 条候选平铺一屏、原始 JSON 直接怼脸上，还说一句「标记已阅」让人不知道是收藏还是看完。现在它按「集群 / 可建链接 / 孤立卡」分组，能筛、能搜、能就地预览，错误也翻成人话。

记忆数据格式与 wire 方法集不变，升级不用迁移。

## 新增与改进

### 候选按类型分组，默认只展开能动手的

- 待处理候选分三类：**集群**（多张卡共享同一实体或触发词，可合并成主题）、**可建链接**（两张卡该连还没连）、**孤立卡**（没有任何连线）
- 孤立卡默认收起——它没有可执行动作，先折叠起来减少首屏噪音；集群与可建链接默认展开
- 组头带数量，一眼看出哪类有活

### 筛选与搜索

- 状态 chip：全部 / 待处理 / 已阅 / 已忽略
- 关键词搜索框，匹配候选标题与卡片的短 id

### 候选行写清「为什么建议这么整理」

- 候选行下方单独一行小字「理由：」——
  - 可建链接：「两张卡都提到实体「a」；都带触发词「b」」（只列非空的那组，都空就写「两张卡有共同关键词」）
  - 集群：「N 张卡都共享实体 / 触发词「term」，可以合并成一个主题」
  - 孤立卡：「这张卡没有和任何卡相连」，有指向已退休卡的旧连线时追加说明
- 理由直接来自候选的 evidence；evidence 缺失或形状不对就**不显示，不编理由**

### 就地预览，删掉页面级 proposal 文本框

- 点候选行里的「预览整理计划」，预览卡就渲染在**那一行正下方**，不再跑到页面底部
- 原先页面底部那个全局 proposal JSON 文本框已经移除——它正是「点第二条候选就报 INVALID_INPUT」的根源：文本框是单一的，第二条候选会拿第一条的骨架去发请求，服务端校验「links 里的卡必须是本候选的源卡」必然失败
- 手写 proposal 收进默认折叠的「高级：手动编辑 proposal」区，给需要调参的人留着
- **孤立卡不再提供预览入口**：它没有第二张卡可连，硬点只会得到一条校验错误。现在按钮不出现，真要走这条路会在本地提示「这张卡还没有和任何卡相连，没有可预览的整理计划」，一个请求都不发

### 预览卡说人话

- 标题 + 2 到 3 行正文，按计划类型分开写：
  - **连起来**（link）：把哪张卡连到哪张卡、关系是什么，并说明「连错了到卡片详情删连线即可」
  - **合并进主题**（merge-topic）：合并进哪个主题，以及「合并后源卡会退休，这一步不可撤销」
  - **core 瘦身**（thin-core）：只报「core 正文 X → Y 字」
  - 未知类型原样显示
- 确认按钮按类型分文案：link 用「就这么连起来」、merge-topic 用红色「确认合并（不可撤销）」、thin-core 用红色「确认瘦身」、未知类型兜底「确认执行」
- thin-core 的按钮确实存在，但点下去服务端一律拒 UNSUPPORTED——它是草案，执行器不接
- planId / planDigest / 摘要与整个原始 diff 收进默认折叠的「原始信息」

### 错误提示翻成人话

- 中文场景文案 + 下一步动作，原始 code 收进「技术细节」折叠区
- 不再出现 `connection: invalid server-response failure` 这类传输层裸文案

### 候选过期就地标注 + 顶部重新分析入口

在面板之外直接改卡片（连/断线、改内容）会让队列里引用它的候选 revision 过期，这时候点预览必然吃 REVISION_CONFLICT。以前是「点了才报错」，现在提前标出来：

- 过期候选行显示「卡片已改」徽章 + 原因小字
- 该行的「预览整理计划」与「合并进主题」按钮置灰（集群候选的合并走同一条 revision 校验，一并挡掉）
- 「稍后再说」「忽略」仍可用
- 过期数大于 0 时页顶出现提示条与「重新分析」按钮，直接复用「分析整理候选」的分析路径，不新造 RPC
- 按钮提示里写明「刷新」只重新读取队列快照、不会重新分析

### 执行完的候选会从队列里退场

以前连完一条线，那条候选还留在队列里，再点预览就是 REVISION_CONFLICT——因为连线的动作把源卡 revision 从 5 涨到 6，而候选项还绑着 5。现在计划执行成功后该候选直接移出队列、队列版本前进；想再对同一对卡连一次，点「分析整理候选」重新分析即可（不是点「刷新」）。

## 修复

- 点第二条候选必报 INVALID_INPUT：全局单一 proposal 文本框串了候选（见上）
- 孤立卡的「预览整理计划」必然报 INVALID_INPUT：骨架取不到第二张源卡，退化成占位符，被服务端 id 字符集校验拒掉
- 连线执行后队列不收敛，同一对卡二次连线必报 REVISION_CONFLICT
- 未知候选类型（服务端将来新增的种类）会被静默丢弃、不进任何分组；现在统一兜进「其他」组并保留原文
- REVISION_CONFLICT 的提示原来指向「刷新」，但刷新救不回来；改指「分析整理候选」

## 兼容与限制

- wire 方法集不变：仍为 10 个 wire 方法（`src/plugin/client-rpc.mjs` 的 `CONTRACT_METHODS`：getStatus / getMemoryView / getGraph / executeTool / listCandidates / analyze / reviewCandidate / previewPlan / executePlan / getTimeline）。其中 `getStatus` 是纯内存投影，不进在途排空；`DRAINED_MANAGEMENT_METHODS` 是其余 9 个
- 记忆数据格式不变，升级无数据迁移
- 需要 DSH `>=0.2.1-rc.2 <0.3.0`、Node `>=24`
- 「已阅」「已忽略」目前没有撤销入口（协议不支持）；「稍后再说」只是把候选收起来，**不删除任何记忆**
- 整理 / 结网会真写 `sparks.json`，第一次用之前建议先备份一次 dataRoot

## 本次明确不做

- **F6 自动触发**：候选的自动分析 / 定时整理。本版整理与遗忘页仍是手动发起（点「分析整理候选」/「分析遗忘候选」），不做后台定时自动跑
- **心跳联动**：与心跳插件（dsh-heartbeat）的联动不做——整理与遗忘页不读取、不响应心跳状态，所有整理 / 遗忘动作都由用户在页面上手动发起
